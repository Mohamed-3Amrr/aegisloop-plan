# Applied brief — AegisLoop personal understanding edition

Date: 24 October 2026 (Cairo).

## Goal

Improve the existing AegisLoop website as a personal learning and reference space for the project coordinator. Help the user understand all workstreams, explain the system to teammates, know why the parts exist and return to the relevant detail without rereading all 70 guides.

This corrects the previous management-dashboard proposal. The user does not want a delivery/reporting workflow, team progress board, meeting-update process, actual blocker dashboard or manual completion tracker inside this site.

## Preserve

Keep the existing site/project, visual identity, 70 package IDs, primary/support ownership, scope, dependencies, decisions, research, risks, sources, hosting plan, on-prem stages and New/Updated history. Do not restart completed research or select new technologies for this learning layer.

Existing package outputs and acceptance criteria remain part of the technical plan. Explain what they mean; do not claim they were delivered or reviewed.

## Personal learning experience

1. Make the homepage a clear entry into understanding the project, with a short scope statement and links to the reading route, teaching case, people, questions and navigation guide.
2. Add a Study Desk with six capability chapters covering every package: intelligence, asset evidence, applicability/priority, AI/UX, controlled remediation and platform/hosting. State that reading order differs from implementation dependencies.
3. Follow one explicitly fictional case through source evidence, inventory, tri-state applicability, priority/grouping, grounded explanation, approval, isolated execution, independent verification and traceable history. Never invent a real CVE/fixed-version assertion.
4. Explain each person's domain, relevant tools, conditional choices, boundaries and technical connections. Hams leads AI and UX design; Omar implements the platform/UI. Amr builds collection/execution, not only tests. Shams owns intelligence/tool trust and Mahrous applicability/policy.
5. Explain every sidebar tab with its meaning, exact situation for using it, a project-specific example, its limits and a next link. Decision Log is technical reasoning; Risk Radar is a collection of possible failure modes, not a live incident board.
6. Add a compact understanding layer for all 70 packages using their actual research question, method, concrete output and dependency/consumer relationships. Keep implementation detail expandable.
7. Provide a searchable project glossary, answered discussion questions and a presentation talk track. Explain CVE versus finding, inventory versus applicability, RAG versus current tools/database, classification versus generation, approval versus execution, and local inference versus disconnected operation.
8. Provide a static question template to bring a precise package/decision question back to the conversation. Do not store personal notes, scores, questions or secrets on the public site.
9. Provide downloadable personal study material and this corrected brief. Website content stays primarily clear English, with short Egyptian Arabic explanations where they improve understanding.

## Remove the reporting interpretation

Remove browser-local completion controls and labels derived from them from the current UI. Show static planned prerequisites, consumers and parallel candidates instead of reporting Ready/In Progress/Done/Blocked. Do not read, erase or overwrite any legacy local browser notes.

Keep conceptual interaction—navigation, expandable explanations, case-stage selection, term search and change comparison. These interactions are for reading; they do not create a dynamic team-management application.

No new status reporting, evidence-submission form, completion percentage, learning score, meeting routine or synthetic team activity should be introduced.

## ClickUp boundary

ClickUp is not necessary for this edition. Do not access or modify the workspace, invent a live connection, or add authentication/infrastructure merely for study features. A future convenient integration can be assessed separately with the exact workspace and supported authorization. Existing prepared exports are not synchronization.

## Truthfulness and provenance

Separate explanatory text updates, original research/source review dates, proposed experiments and actual results. New/Updated means the plan or explanation changed. No badge means that a task, risk review, source revalidation or product experiment happened.

Reuse the existing evidence. If a genuine new technical question arises, use targeted official research and preserve unresolved choices as Needs Validation.

## Validation and publication

Verify all learning routes, nine case stages, five person explanations, 70 package links, glossary search, navigation help, retained change history and downloads. Verify that the normal UI contains no progress controls or inferred completion/blocker state and that no personal data is persisted.

Preserve all original work-package content and ownership/dependency logic. Publish the improved existing site with its existing audience and provide the user a direct Study Desk entry point.
